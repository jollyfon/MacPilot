# 双设备在旁边仍自动锁屏：2026-10-15 排查

## 已观察到的事件

- 本机运行 1.2.2-beta.12；配置为 iPhone + Apple Watch，关系 `any`，锁屏 RSSI -80，信号超时 60 秒。
- 22:04:07、22:08:22 两次均由 BLE 模块记录 `signal timeout fired` → `presence ... reason=lost` → `locking due to presence loss`。用户确认两台设备都未离开。
- iPhone 有已认证 UUID 别名；这一时段系统只恢复了手机别名的连接，没有获得所选手表 UUID 的有效信号。因此不是两条正常运行的检测通路分别报告设备走远，而是一条通路没有建立，剩余通路失联后触发锁屏。
- `bluetoothd` 在 22:03:08、22:07:23 记录手机连接 `remotely-initiated` 断开；随后 MacPilot 发起重连，在信号超时时又发送 `CBMsgIdCancelPeripheralConnection`，取消仍在建立的连接。
- 测试日志最后更新于 21:26；当时的另一聊天正在执行发布资产核验，没有执行真实锁屏测试。

## 源码中的故障链

1. 扫描关闭重复广播，CoreBluetooth 会合并同一设备的发现事件。原来的长期扫描不能承担连续的广播测距；被动设备或未连上的手表缺少周期重新发现机制。
2. `didDiscover` 以 `activeModeTimer == nil` 为条件处理广播。但定时器在断连后仍存在，导致重新发现的有效广播也被忽略。
3. 超时在重新发现之前直接撤销存在状态并锁屏，随后销毁整个 central，取消尚未完成的连接。单台设备 RSSI 请求故障也会走全局重置路径。
4. 已缓存外设对象就被当作“不需要扫描”；即使手表已经断连或还没成功读过 RSSI，手机的首次 RSSI 回调仍可能停止扫描。弱信号延迟回调也没有在采样过期时终止锁屏决定。

## 修复

- 对每个逻辑设备独立检查采样新鲜度；缺少新信号时，最多每 10 秒重新启动一次去重扫描并尝试恢复已知设备。已认证别名仍归属于同一逻辑设备。
- 所有匹配已配置身份的发现广播均参与 RSSI 更新，不再受主动读取定时器是否存在的影响。
- 只有每个逻辑设备都有已连接的 RSSI 轮询，才允许停止发现扫描。弱信号计时回调只接受仍然新鲜的远距离样本，过期样本交给信号丢失复核处理。
- 断连后立即尝试保留连接的重新发现；普通信号超时及 RSSI 故障恢复只刷新扫描，不销毁 central、不清空另一台设备状态。RSSI 请求超时释放请求门，允许后续重试。
- 信号到期立即撤销其解锁用的新鲜信号资格；锁屏前做一次有期限的重新发现复核（`min(10, max(1, signalTimeout / 3))` 秒）。无新信号仍会锁屏；重新扫描本身不能续期。
- 真实弱 RSSI 的离开延时和 `any` / `all` 规则保留。没有修改任何持久化键或用户设置，也不按名称猜测新的设备身份。
- 缺少信号时的限频日志记录每个逻辑设备及别名的 RSSI、采样年龄和连接状态，补足默认日志过滤 debug 采样后留下的排障盲区。

## 验证边界

自动化回归使用假蓝牙扫描器、可控时钟和锁屏操作替身，覆盖双设备同步超时、单台恢复、持续失联、主动定时器残留、逻辑设备与别名、扫描限频和关闭释放。

- 定向 BLE / 配置回归：129 项通过。
- 红绿验证：恢复旧广播过滤判断时，断连后广播刷新用例确实失败；去掉旧判断后通过。
- 全新构建目录的 Release `-warnings-as-errors` 构建通过。
- 首轮完整回归暴露了一个恢复用例共享真实时钟造成的额外扫描计数问题，已改用可控时钟；其余截图、视频及唤醒时间断言按隔离方式核验，不能把首轮完整回归描述为全部通过。
- 新回归套件已纳入 GitHub CI。

这些证据不能证明手表所选 UUID 在真实系统中仍可被发现，也不能证明新版本已通过持续的真实双设备验收。所选手表 UUID 当时未收到信号的底层原因尚不能从留存日志确认；不得以重命名、猜测 UUID 或测试通过代替现场验证。本机安装不随发布替换。
